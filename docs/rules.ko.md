# flow-atlas 규칙

적용 시점: 이슈와 PR을 만들 때, 영역·사용자 흐름·범위를 바꿀 때. [English](rules.md)

## TRACK-01 · 영역과 사용자 흐름 목록은 파일 하나가 정본이다.

- 할 일: 제품을 영역 → 사용자 흐름으로 나눠 `flow-atlas.json`에 적는다. 이슈 양식의 선택지와 라벨은 이 파일에서 생성하고 직접 고치지 않는다. 이번 버전에서 뺀 흐름은 지우지 않고 `scope`를 `out`으로 둔다. flow-atlas를 들이기 전에 이미 만든 흐름에는 `shipped`를 `true`로 적는다.
- 완료 증거: 생성 파일이 최신이라는 검사 결과, 제외한 흐름과 다시 볼 조건.

## TRACK-02 · 이슈에는 무엇을 왜 하는지 적는다.

- 할 일: 이슈 하나는 흐름 하나에 속한다. 사용자가 얻는 결과를 기술 용어 없이 적고, 작업 항목은 체크박스로 쓴다. 구현 방법은 이슈가 아니라 PR에 적는다.
- 완료 증거: 흐름 라벨이 붙은 이슈, 체크박스 진행 상태.

## TRACK-03 · PR에는 어떻게 바꿨고 무엇으로 확인했는지 적는다.

- 할 일: 연결 이슈, 변경 유형, 달라지는 동작, 검증을 적는다. 검증하지 못한 부분은 비워 두지 않고 그 사실과 이유를 적는다.
- 완료 증거: PR 본문 검사 통과. 검사는 항목이 채워졌는지만 보며 검증 내용이 사실인지는 판정하지 않는다.

## TRACK-04 · 이슈와 PR의 관계를 키워드로 구분한다.

- 할 일: 이 PR로 이슈가 끝나면 `Closes #번호`, 일부만 진행하면 `Refs #번호`를 쓴다. 계획에 없던 작업은 `이슈 없음: 사유`를 적어 드러낸다. 영어 서식에서는 `No issue: <reason>`이다.
- 완료 증거: PR 없는 이슈와 이슈 없는 PR을 목록으로 뽑을 수 있다.
- 주의: GitHub는 기본 브랜치로 가는 PR의 `Closes`만 연결로 기록한다. `Refs`는 GitHub 키워드가 아니며 이슈 타임라인의 언급으로만 남는다.

## TRACK-05 · 오너에게 묻는 질문은 이슈나 PR의 댓글로 남긴다.

- 할 일: 구현 중 판단이 필요한 질문을 [결정 요청 댓글](decision-comment.ko.md) 서식으로 남긴다. 범위에 관한 질문은 이슈에, 구현 방법에 관한 질문은 PR에 쓴다. 대화에서 바로 답을 받은 질문도 결정된 상태로 남긴다. 답을 받으면 같은 댓글을 고쳐 상태와 결정을 적는다.
- 완료 증거: 대기 중인 질문과 결정된 질문을 이슈·PR별로 목록으로 뽑을 수 있다.
